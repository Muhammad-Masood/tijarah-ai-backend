## What system/approach is used

The repository uses **Poetry** as the primary Python package manager for dependency declaration, resolution, and lockfile management. The project is a single-package application (`neurocom-backend`, version `0.1.0`) declared in `pyproject.toml`. A Poetry-generated `poetry.lock` file pins every transitive dependency to an exact version along with per-distribution SHA256 hashes, ensuring reproducible installs across environments.

A secondary, legacy distribution exists under `neurocom_backend/python/` — a standalone setuptools-based package named `lazop-sdk-python` (version `1.1.0`) that ships its own `setup.py` and `.egg-info` metadata. This appears to be a vendored third-party SDK (Lazada/Lazop) that is not managed by Poetry and has no runtime dependencies declared.

## Key files and packages

- `pyproject.toml` — declares the project metadata, Python version constraint (`^3.11`), all direct dependencies (FastAPI, Uvicorn, SQLModel, Pydantic v2, JWT, bcrypt, OpenAI, LangChain ecosystem, ChromaDB, Redis, etc.), and the Poetry build backend (`poetry.core.masonry.api`).
- `poetry.lock` — generated lockfile (Poetry 2.3.2) pinning every resolved dependency to an exact version and hash; it is committed to the repo and should not be edited by hand.
- `.python-version` — specifies `3.12.10`, which is compatible with the `^3.11` constraint in `pyproject.toml`.
- `Makefile` — provides a `run` target that invokes `poetry run uvicorn ...`, tying development execution to the Poetry-managed environment.
- `README.md` — documents both `make run` and `poetry run uvicorn ...` as the standard ways to start the service.
- `neurocom_backend/python/setup.py` + `neurocom_backend/python/lazop/` — vendored SDK package built with setuptools, independent of Poetry.

## Architecture and conventions

- **Single source of truth**: All application dependencies are declared exclusively in `pyproject.toml`; there is no `requirements.txt`, `Pipfile`, or other parallel manifest.
- **Lockfile-driven reproducibility**: `poetry.lock` is committed alongside the codebase. The lockfile header states it is "automatically @generated by Poetry 2.3.2 and should not be changed by hand", indicating that manual edits are discouraged and updates should go through Poetry commands.
- **Version ranges vs. pinned versions**: Direct dependencies use caret ranges (e.g., `fastapi = "^0.115.12"`, `requests = "^2.32.3"`) allowing minor/patch upgrades within the same major version. Two exceptions are pinned to exact versions: `openai = "1.109.1"` and `langchain-openai = "^1.1.6"` (the latter uses a range). The root directory also contains bare version-number files `1.1.6` and `1.109.1`, which appear to mirror pinned dependency versions but are not referenced by any build script.
- **Extras usage**: Optional features are enabled via Poetry extras syntax, e.g., `uvicorn` with `extras = ["standard"]`, `pydantic` with `extras = ["email"]`, `redis` with `extras = ["hiredis"]`.
- **Python version policy**: The project requires Python `^3.11` in `pyproject.toml` and pins the interpreter to `3.12.10` in `.python-version`, keeping the dev/runtime interpreter aligned with the declared constraint.
- **Vendored SDK isolation**: The Lazop SDK lives under `neurocom_backend/python/` as a separate setuptools distribution (`lazop-sdk-python`). It is not imported via Poetry and has an empty `install_requires=[]`, meaning it is consumed directly from source rather than installed as a package. Its presence suggests a vendoring strategy for a third-party SDK that cannot be pulled from PyPI or must be customized locally.
- **No private registry configuration found**: There is no `poetry.toml`, `.netrc`, or `[tool.poetry.source]` section visible in the checked files, so no custom/private PyPI source is configured at this level.

## Conventions and constraints

- Dependencies are added only via `pyproject.toml` under `[tool.poetry.dependencies]`; no `pip install` invocations or `requirements.txt` files exist in the main project tree.
- The lockfile is treated as immutable source-of-truth: the header explicitly says it is auto-generated and should not be edited by hand. Updates should be performed through Poetry's update/add/remove commands.
- Development runs are funneled through `make run`, which delegates to `poetry run uvicorn`, ensuring the Poetry virtual environment is always used.
- The vendored `lazop-sdk-python` package follows a conventional setuptools layout (`setup.py` + `find_packages()`) and is kept separate from the Poetry-managed app dependencies, suggesting a deliberate boundary between managed and vendored code.
- No explicit rules were found governing how dependency versions are chosen beyond the standard Poetry caret-range convention; however, the presence of exact-pinned versions for `openai` and the bare version-number files in the repo root indicates ad-hoc pinning decisions for specific integrations.
