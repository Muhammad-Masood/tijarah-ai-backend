## Build System Overview

This repository uses **Poetry** as the sole build, dependency, and packaging system for a FastAPI + LangChain AI service. There are no Dockerfiles, CI pipelines, Makefile targets beyond a single local dev runner, or shell-based build scripts in this repo.

## Key Files and Packages

- `pyproject.toml` — Poetry project manifest declaring the package name (`neurocom-backend`, version `0.1.0`), Python constraint (`^3.11`), all runtime dependencies (FastAPI, Uvicorn, SQLModel, OpenAI, Google GenAI, LangChain, ChromaDB, Redis, etc.), and the build backend (`poetry.core.masonry.api`).
- `poetry.lock` — Deterministic lockfile generated by Poetry 2.3.2; pins every transitive dependency with per-platform wheel hashes, ensuring reproducible installs across environments.
- `.python-version` — Declares the exact CPython version to use (`3.12.10`), typically consumed by `pyenv`/`asdf` to select the interpreter before running Poetry.
- `Makefile` — Contains a single `run` target that invokes `poetry run uvicorn neurocom_backend.main:app --host 0.0.0.0 --port 8000 --reload`, providing a one-command development server start.
- Root-level files `1.1.6` and `1.109.1` — Appear to be vendored version markers for `langchain-openai==1.1.6` and `openai==1.109.1` respectively, likely used as quick reference or pinned versions outside Poetry's normal flow.

## Architecture and Conventions

- **Dependency management**: All third-party packages are declared exclusively in `pyproject.toml`. The `poetry.lock` file is committed alongside it, so developers install via `poetry install` to get an exact, reproducible environment. No `requirements.txt` exists.
- **Python version pinning**: Two layers of pinning coexist — `pyproject.toml` constrains the major/minor range (`^3.11`) while `.python-version` pins the exact patch (`3.12.10`). This ensures both Poetry resolves against the right interpreter and tools like `pyenv` select the correct binary.
- **Build backend**: Uses Poetry's built-in `poetry-core` masonry backend; there is no custom `setup.py` for the main application. A separate legacy `setup.py` exists only under `neurocom_backend/python/` for the bundled `lazop_sdk_python` package, which is unrelated to the main service build.
- **Runtime entry point**: The ASGI app lives at `neurocom_backend.main:app`; the Makefile target and any deployment invocation must reference this module path.
- **No containerization or CI in-tree**: There is no `Dockerfile`, `docker-compose.yml`, GitHub Actions workflow, or other CI/build pipeline configuration checked into this repository. Packaging for distribution is not configured beyond Poetry's default sdist/wheel generation.

## Conventions and Constraints

- Use `poetry run <command>` to execute anything inside the managed virtual environment (e.g., `poetry run uvicorn ...`, `poetry run python -m pytest ...`).
- Do not edit `poetry.lock` by hand — it is auto-generated and carries per-platform wheel hashes; changes should come from `poetry add` / `poetry update`.
- Keep the Python version in `.python-version` in sync with what `pyproject.toml` allows; mismatches will cause Poetry to refuse to resolve or install.
- Development server startup is standardized through the `make run` target, which binds to `0.0.0.0:8000` with hot-reload enabled.
- Versioning of the application itself is isolated in `pyproject.toml` (`version = "0.1.0"`); there is no semantic versioning automation or release script in this repo.
