## System / Approach

The repository uses **Poetry** as its sole Python package manager and dependency resolver. All third-party dependencies are declared in `pyproject.toml` under `[tool.poetry.dependencies]`, and the exact resolved versions (including transitive dependencies) are pinned in a committed `poetry.lock` file generated by Poetry 2.3.2. The project targets Python 3.11+ via the caret constraint `^3.11` in `pyproject.toml`, while `.python-version` pins the development interpreter to `3.12.10` for local tooling.

## Key Files

- `pyproject.toml` — declares the project metadata (`name = "neurocom-backend"`, `version = "0.1.0`), all runtime dependencies, extras, and the build backend (`poetry.core.masonry.api`).
- `poetry.lock` — deterministic lockfile listing every resolved package with its exact version, supported Python ranges, and per-distribution SHA-256 hashes; it is auto-generated and should not be edited by hand.
- `Makefile` — provides a single `make run` target that invokes `poetry run uvicorn neurocom_backend.main:app ...`, ensuring all commands execute inside the Poetry-managed environment.
- `.python-version` — tells pyenv (or compatible tools) which CPython version to use locally.
- `neurocom_backend/python/setup.py` — an isolated, legacy-style `setup.py`/`.egg-info` package (`lazop_sdk_python`) bundled alongside the app; this is a separate distribution artifact and does not participate in the main Poetry dependency graph.

## Architecture and Conventions

- **Single source of truth**: Dependencies live only in `pyproject.toml`; there are no `requirements.txt`, `Pipfile`, or `setup.cfg` entries for runtime deps.
- **Version constraints**: Most packages use caret (`^`) constraints (e.g., `fastapi = "^0.115.12"`, `langchain = "^1.2.0"`, `redis = {extras = ["hiredis"], version = "^8.1.0"}`), allowing compatible minor/patch updates while preventing breaking major bumps. A few dependencies are pinned to exact versions (e.g., `openai = "1.109.1"`, `mcp = {extras = ["cli"], version = "^1.8.0"}`), likely due to known compatibility requirements within the AI stack.
- **Lockfile-driven installs**: CI and production builds should resolve from `poetry.lock` (via `poetry install --no-interaction`) to guarantee reproducible environments. The lockfile header explicitly states it is auto-generated and must not be changed by hand.
- **Extras usage**: Optional features are expressed via Poetry extras, notably `uvicorn[standard]` and `redis[hiredis]`, rather than ad-hoc pip flags.
- **Build system**: The `[build-system]` section pins `poetry-core` as the build backend, so building distributions also goes through Poetry's Masonry API.
- **No vendoring**: There is no `vendor/` directory or inline vendored code for third-party libraries; all external code comes from PyPI via Poetry.
- **Private registries**: No custom PyPI index, `pip.conf`, or Poetry repository configuration was found in the inspected files; dependencies are resolved from the default PyPI.

## Conventions and Constraints

- Add new dependencies by editing `pyproject.toml` under `[tool.poetry.dependencies]`, then regenerate the lockfile with Poetry so `poetry.lock` stays in sync.
- Do not edit `poetry.lock` manually; it is marked as auto-generated and contains per-file checksums used by Poetry to verify integrity.
- Keep the Python version constraint in `pyproject.toml` aligned with `.python-version` to avoid dev/prod mismatches.
- Use caret version ranges for most packages to balance stability with access to bugfix/minor updates; reserve exact pins for packages with strict compatibility needs (as seen with `openai`).
- Run all commands through `poetry run ...` (as shown in the `Makefile`) to ensure the isolated environment is used consistently across development and deployment.
