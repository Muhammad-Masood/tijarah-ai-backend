## Build System Overview

This repository uses **Poetry** as the sole build, dependency, and packaging system for the FastAPI backend. There are no Dockerfiles, CI pipelines, Makefile targets beyond a single dev convenience target, or shell scripts — the project is intentionally lightweight.

## Key Files and Their Roles

- `pyproject.toml` — Central manifest declaring the package (`neurocom-backend`, version `0.1.0`), Python version constraint (`^3.11`), all runtime dependencies (FastAPI, Uvicorn, SQLModel, OpenAI, LangChain, Redis, etc.), and the build backend (`poetry.core.masonry.api`).
- `poetry.lock` — Deterministic lockfile generated by Poetry 2.3.2; pins every transitive dependency with SHA-256 hashes across many platforms (manylinux, musllinux, macOS universal2, Windows). This is the source of truth for reproducible installs.
- `.python-version` — Declares `3.12.10`, used by pyenv-style tooling to select the interpreter.
- `Makefile` — Contains only one target: `make run`, which executes `poetry run uvicorn neurocom_backend.main:app --host 0.0.0.0 --port 8000 --reload`. No test, lint, build, or publish targets exist.
- Root-level files `1.1.6` and `1.109.1` — Appear to be vendored version markers for `langchain-openai` and `openai` respectively (matching versions declared in `pyproject.toml`); they are not part of any build script.
- `neurocom_backend/python/setup.py` and `neurocom_backend/python/` — A separate, legacy setuptools distribution (`lazop_sdk_python`) bundled inside the repo; unrelated to the main Poetry project.

## Architecture and Conventions

- **Single-source-of-truth dependencies**: All third-party packages are declared exclusively in `pyproject.toml`; nothing is installed via `requirements.txt` or pip directly.
- **Reproducible environments**: The committed `poetry.lock` ensures that `poetry install` resolves the exact same wheel binaries on every machine.
- **Dev-only entrypoint**: Development runs through `make run`, which delegates to Poetry's virtual environment and invokes Uvicorn with hot-reload enabled (`--reload`).
- **No containerization or CI**: There is no `Dockerfile`, no GitHub Actions/GitLab CI config, no `build.sh`, and no publish/release pipeline in this repository. Packaging is configured for Poetry's built-in `poetry build` / `poetry publish` flow but no such commands are invoked here.
- **Python version pinning**: Two layers enforce the interpreter — `pyproject.toml` requires `^3.11` and `.python-version` pins `3.12.10` for local tooling.

## Conventions and Constraints

- Dependencies must be added to `pyproject.toml` under `[tool.poetry.dependencies]`; the lockfile is regenerated via Poetry (the header states it is "automatically @generated" and "should not be changed by hand").
- The project has no explicit lint/test/build targets in the Makefile; development workflow centers on `make run`.
- The embedded `neurocom_backend/python/` subpackage uses a separate `setup.py` and produces an egg distribution independently of the Poetry project — it is treated as a vendored SDK rather than part of the main build.
- Version numbers in `pyproject.toml` use caret ranges (e.g. `^0.115.12` for FastAPI), allowing compatible updates while the lockfile locks exact versions.
